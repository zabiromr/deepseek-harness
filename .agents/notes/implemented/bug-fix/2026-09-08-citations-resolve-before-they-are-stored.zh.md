# Agent Note: 引用在存储之前先完成解析

Status: implemented

[English](2026-09-08-citations-resolve-before-they-are-stored.md) | 中文

## Problem

习得记忆能力缝要求每条教训都引用产生它的会话事件，因为无法对照日志回放的教训不可审计，也就绝不应再次进入提示词。`assertEvidence` 强制引用必须存在、序号为序数且递增，但没有任何环节检查这些内容是否指向真实存在的东西。

`dsh-tool-self-reflect` 中的 `resolveEvidence` 按模型写下的原样读取引用：

```ts ignore-check
const session = citation.session ?? fallback
…
return { session: session as SessionId, seq: [...citation.seq] }
```

只有当该字段缺失时，`??` 才会填入调用方会话。模型写下的任何字符串都会被保留，而类型断言直接把它变成 `SessionId`，从不追问这个会话是否存在。序号则完全没有与任何日志比对过。

模型在本工作区记录的第一条教训同时踩中了这两条路径。它引用了 `session: "current"`——一个占位符而非标识符——以及 `seq: [6, 7]`，而在真正记录它的那个会话里，这两个序号是 `agent/inbox/spliced` 与 `step/start`：会话初始化，追加于该教训所描述的工作之前。真正的证据位于 seq 65 到 1170 之间。这条教训被存储、进入摘要，并携带着指向虚无的证据抵达了后续会话的提示词。

这正是[包规则](../../../../packages/AGENTS.md)明确指出的失败：模型与工具 JSON 是校验边界，而由模型写入的字符串断言而来的 `SessionId` 已经未经检查地越过了它。

## Decision

### 写入侧 Consumer 负责解析，服务保留形式检查

`assertEvidence` 维持原样。它在每个 provider 内部运行、与介质无关、且无会话可读，因此顺序与序数性就是它所能判定的全部。可解析性需要会话日志，而唯一持有日志的角色，是接收模型调用的那个 Consumer。

`resolveEvidence` 现在做的是解析而非记录。未指定会话的引用照旧解析为调用方会话。指定了会话的引用：id 与调用方一致时解析为调用方会话，否则通过会话存储解析；两者都无法解析的 id 会连同它给出的名字一起以 `invalid-evidence` 被拒绝。随后每个序号都必须命名所解析会话确实持有的事件，由 `Session.eventAt` 检查。最终存储的始终是所解析会话自身的 id，而非模型给出的字符串。

### 会话存储按可选服务读取，且在调用时读取

该工具通过 `ctx.get` 而非 `inject` 读取 `sessions`。某个组合可以在不挂载会话存储的情况下挂载捕获工具，这样的部署仍可记录引用调用方会话的教训；只有指向其他会话的引用才需要存储，而在没有存储时这类引用会被拒绝，而不是被默默信任。在调用时而非 `apply` 时读取，使得晚于本插件挂载的存储依然能够服务查找。

### schema 陈述该义务

`session` 参数告诉模型：引用当前会话时应省略它，仅在传入某个会话自己报告过的 id 时才填写；`seq` 参数则说明，没有事件承载的序号会被拒绝。读过 schema 的模型已具备写出可解析引用所需的全部信息。

### 证据必须指向工作

要求引用可解析堵住了伪造，也让底下的问题显露出来；而针对该问题的第一版修复——要求被引用事件位于会话首条模型可见消息之处或之后——经生产环境实测证明并不充分。在模型通过真实界面记录的十八条教训中，**有十二条只引用了会话簿记与请求这项工作的那条消息**：`step/start`、`turn/start`、`agent/inbox/spliced`、`session/title`、`request/header` 与 `user/message`。没有一条指向工具调用，尽管这些会话每一个都读过文件才写出正文。`user/message` 本身就是首条模型可见消息，因此引用请求即可满足阈值，并顺带把簿记事件一并带入。

我们对其中八条尝试了在提示词中、紧挨调用之前明确要求引用工具调用。结果毫无变化：八条中有零条引用了工具调用。提示词不是检查。

现在，至少要有一个被引用事件是 `assistant/message`、`tool/call` 或 `tool/result`——模型说了什么、调用了什么，以及调用返回了什么。该规则涵盖了原先的阈值规则，因为这三者都不可能早于首条消息。

这个集合是小而封闭的，而非推导得出。在它之前，有两种结构化分类器经实测后被否决："事件是否派生消息"会在 91 次中的 91 次排除 `tool/call`，因为调用寄载于 assistant 消息之内；而派生消息的 `role` 无法区分工作与请求，因为 `tool/result` 派生出的 role 正是 `user`，与 `user/message` 完全相同。插件自有的事件不可单独作为证据，因为此处无从得知某个贡献类型的含义；依赖它的教训应当与产生它的那次调用一并引用。

### 规则止于何处，以及由什么接替

每条规则都堵住一条路径，同时开启下一条最廉价的路径。伪造的会话变成了样板事件；样板事件变成了请求这项工作的那条消息；请求又变成了扫射——有一条教训引用了序号 1 到 60，另一条则一路每隔十个取一个直到 100。二者都满足上述全部规则，却什么也没有挑选。

再加一条针对引用的规则也无法解决这一点。可解析性、事件类型与位置都是这些数字的属性；而这些事件是否*支持该主张*，则需要读取它们并判断相关性，那是读者的工作，不是校验器的工作。宽度上限会拒绝扫射，转而得到一个恰好等于允许宽度的任意引用，而任何检查都无法将它与经过挑选的引用区分开。

因此，强制执行的规则集止于三条结构性属性——引用可解析、指向工作、可被回放——质量判断则转交给 `scripts/audit-memory-citations.ts`：它将存储与其所指向的日志对读，报告每条教训实际引用了什么，并标出连续或等距的扫射。它在数秒内找出了全部三条。审计能够权衡校验器无法权衡的东西，因为它不必在写入时就作出裁决，也不需要写入方的配合。

## Alternatives considered

- **在 memory 服务内校验。** 被否决，因为这会把会话依赖塞进一个其 provider 均为介质适配器的 Service Definition，从而颠倒能力缝：让某一个 Consumer 的上下文决定服务契约。
- **接受无法解析的会话，并把教训标记为未核验。** 被否决，因为教训能否进入提示词已由地位（standing）决定；再引入第二条信任轴，只会让无法回放的证据不断累积，而不是在写入方仍能修正的那一刻被拒绝。
- **同时从磁盘解析会话。** 属于推迟而非否决。它可以让教训引用本进程从未加载过的会话，这是真实存在的场景；但它需要一个当前能力缝并不拥有的读取方，README 已记录该限制。
- **只校验会话、不检查 `seq`。** 被否决，因为记录在案的实例里会话与序号同时出错，而指向真实会话中毫无意义偏移的引用，同样无法回放。

## Consequences

- 已存储的引用命名的是曾经存在的会话与确实存在的事件，因此回放一条引用是一次查找，而不是一场搜寻。
- 仅存在于磁盘上的会话引用会被拒绝。README 记录了这一点；解除该限制意味着补上一个持久化会话读取方。
- 本次改动之前记录的教训保持原样，没有任何环节重写它们；本工作区中仍有一条引用着 `current`。
- `tool-self-reflect.spec.ts` 中三个用例随行为一同变更：显式指定的外部会话此前会被原样存储，现在除非存储能够读取它，否则会被拒绝。

## Testing

`pnpm run test -- packages/feedback/tool-self-reflect`——18 项通过，覆盖被拒绝的不可读会话、被拒绝的无对应事件序号，以及一条指向存储可读的第二个会话且被接受的引用。种子会话携带三个已完成轮次，因此其引用可以解析；日志为空的会话无法引用任何东西。
